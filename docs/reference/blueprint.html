02 / What the app will do

Your five requirements, expanded.

A proposed capability catalogue. All items below describe intended product behavior; delivery order is defined later in this report.

01
Character & notch

A companion with a job

A customizable slime lives beside the notch. Click to chat, speak, inspect activity, or open the full workspace.

Functions and behavior

Name, palette, eyes, accessories and motion intensity; per-slime instructions, default CLI, model and voice; idle, listening, chewing, thinking, working, asking, resting and error states.

One slime can manage several runs. Its expression summarizes real run state; it never implies success before the runtime confirms it.

02
CLI control & monitoring

One place for your agents

Launch a selected local CLI, stream its work, answer questions and handle approvals without hunting through terminals.

Functions and behavior

Session list, current tool, project, elapsed time, output, artifacts, cancel and resume where supported. Observe external sessions through supported hooks or event feeds.

Label each session Managed or Observed. Only show controls that the active adapter can actually perform.

03
Projects & tasks

Work survives the conversation

Give each project folders, instructions and reference material. Turn a message into a durable task and assign a slime.

Functions and behavior

Board and list views; priority, labels, due dates, subtasks, dependencies, comments, attachments and run history. Queue tasks and review outputs before marking work accepted.

Task ≠ run ≠ provider session. Retries create runs; switching providers carries an explicit summary and artifacts, not an imaginary shared context window.

04
Voice & chat

Talk to your workspace

Click the slime or use a shortcut, speak a request, review the transcript and send it to the selected agent.

Functions and behavior

Push-to-talk, visible microphone indicator, transcript editing, text input, streaming response, optional speech output, stop and cancel.

Transcription and speech are pluggable services. A local CLI can still call a cloud model; local execution does not mean offline inference.

05
Multimodal inbox

Feed it your files

Drop files or a folder on the slime. It chews while the app inventories and processes the material, then presents a summary or useful output.

Functions and behavior

Text/code/PDF first, images through a vision-capable model, audio through transcription, office files through extraction, video through sampled frames and audio in later stages.

Display accepted, skipped and failed files. Check provider/model capabilities. The animation represents actual ingestion progress, not a fixed pretend completion.

06
File organization

Put everything in its place

Ask the slime to rename, classify or move files to a destination you choose. Review the proposed changes and apply them.

Functions and behavior

Before/after path preview; collisions; duplicate candidates; copy or move; operation journal; partial failure recovery; conditional undo.

The agent proposes a structured plan. A dedicated file executor validates and applies it. Undo checks that files have not subsequently changed.

07
Lark, Slack & Linear

Bring work in from your tools

Use authorized connections to bring messages, documents and issues into projects, then prepare updates in context.

Functions and behavior

Find context, create tasks from selected messages, link Linear issues, draft replies, attach artifacts and optionally send explicitly requested updates.

A connector exposes declared read/write actions per account. Receiving a message does not automatically grant its sender control over the Mac.

08
Usage & limits

Know what is still available

See per-run consumption and account limits in one panel, with a source and last-updated time.

Functions and behavior

Input/output/cached tokens when provided; reported or estimated cost; account windows and reset times; stale/unknown states; configurable alerts.

Never infer a weekly limit from token counts. Never add account snapshots across sessions: those may refer to the same shared quota.

03 / System map

The character is the front door.

The task system owns work and history. Provider adapters translate a common set of events into the capabilities each CLI actually supports. Select a block to inspect its responsibility.

Commands → task/run IDs → adapter → processEvents ← durable journal ← normalized stream ← runtime
Project → Task → Run

The project provides roots, instructions and resources. The task represents the outcome. Each run records a concrete attempt with inputs, status and outputs.

SlimeProfile → RuntimeConfig

Appearance, personality and voice are independent of provider, model, executable path and work directory. Several tasks may use one profile.

Run → SessionRef + PendingInput[]

Provider session IDs support continuity. Approval and question IDs belong to the exact run, session and turn; expired requests cannot be answered.

Recommended native foundation: SwiftUI for the workspace and settings; AppKit panels for notch placement, keyboard focus and drag/drop; a Swift concurrency runtime layer for process ownership; SQLite for durable records; Keychain for app-owned connector credentials. This is a proposed architecture, not an existing implementation.

Runtime lifetime: in the first version, closing the panel leaves the menu-bar app and managed processes running. Quitting the app must explicitly stop or detach supported sessions. A separately installed helper can later support work that survives UI app exits; it is not required for the first usable slice.

Managed sessions

The app starts the process, owns its protocol, records its provider session ID and receives correlated events. This is the reliable path for interactive control.

start → stream → request input → respond → complete

Observed sessions

The terminal or another tool owns the session. The app receives supported lifecycle and usage telemetry. It shows “Observed” and only offers actions backed by an actual control channel.

discover → subscribe → display → open owner
05 / Signature interaction

Feed. Understand. Organize.

The chewing animation makes the ingestion visible. The useful result is a source-linked answer or a concrete file-operation plan.

When you feed a folder

  1. Inventory the selectionIdentify files, sizes and formats within the selected root. Cap traversal and skip symlinks escaping the selection, hidden/system material and unsupported items by policy.
  2. Build a manifestShow what was accepted, skipped and why. Track source paths, hashes and extraction status. Read originals in place; make staged derivatives only when needed.
  3. Prepare model inputExtract text or OCR; chunk large collections; transcribe audio; pass images only to a compatible model. Keep citations tied to pages, timestamps or file paths.
  4. Run the requested analysisStart a task on the chosen CLI. Surface progress and missing capabilities. Treat document contents as material to analyze, not instructions granting tools or access.
  5. Present results and follow-upsSummary, questions, searchable notes and generated artifacts. Record failed files so a partial result cannot appear complete.

When you ask it to organize

  1. Propose, then previewThe agent returns structured operations with source, destination and reason. Show affected files and totals; distinguish copy, move, rename and deletion.
  2. Validate the planResolve paths, verify allowed roots and current file hashes, handle collisions, reject cycles and unsafe overwrites. No arbitrary shell command is accepted as a move plan.
  3. Apply an authorized planThe file executor applies approved operations, journals each result and handles cross-volume moves as copy/verify/remove. Stop on uncertain or changed inputs.
  4. Recover or undoReconcile interrupted work from the journal. Undo only when destination contents and source availability still permit a safe reversal; otherwise show the conflict.

Example plan · illustrative

MOVE  Downloads/notes.pdf
   →  Research/References/notes.pdf

RENAME  Research/scan-001.png
     →  Research/meeting-whiteboard.png

COPY  Downloads/brief.md
   →  Research/Briefs/brief.md

3 operations · 0 deletions · collision checks required
Files remain unchanged until the plan is applied.

06 / Project management & connected work

Borrow the model. Build your own experience.

Multica is a useful reference for persistent projects, issues, agent profiles and runtime-bound executions. The notch should provide quick attention; the full window should handle planning and history.

Workspace surfaces

  • Today: running tasks, requests waiting for you, completed outputs.
  • Projects: repository/folder roots, instructions, resources and task boards.
  • Task detail: brief, discussions, checklist, attachments and chronological runs.
  • Agents: slimes, CLI configurations, available capabilities and health.
  • Files: incoming material, summaries, outputs and organization history.
  • Usage: source-tagged account snapshots and separately measured run consumption.

States that mean something

Task: backlog → ready → in progress → review → done; also blocked and canceled.

Run: queued → starting → running → waiting for approval / answer → succeeded, failed or canceled.

Separation: a successful process does not automatically mean the task meets your acceptance criteria. A disconnected observer does not mean an agent has stopped.

Concurrency: bounded active runs, serialized writes to shared folders and optional isolated worktrees for repository work.

Connector behavior

  • Lark: selected chats, documents and tasks as project context; separate global Lark and mainland Feishu account configuration.
  • Slack: authorized channel/thread lookup, task capture and requested replies.
  • Linear: issue lookup, import/link, status mapping and authorized updates.
  • Use stable external IDs, deduplication and revision checks. Start with manual linking; add automatic synchronization after conflicts have a defined policy.

These are proposed scopes. Official connector capabilities, scopes and distribution requirements must be verified during each connector implementation.

Connection architecture

Expose approved connector actions through a tool gateway or provider-compatible MCP configuration. Keep credentials in Keychain and bind tool grants to the current account, project and run.

Local-only v1 can use manual refresh and outbound calls. Inbound events require the service’s supported persistent connection, polling or a small relay; a sleeping Mac cannot provide always-on delivery.

Show a reviewable outbound draft. Send only when the user has authorized that action or configured a specific automation.

Reference decision: reuse the separation of project, task, profile and execution as a design pattern. Do not embed Multica by default. Its repository license includes additional hosting, commercial distribution and attribution conditions; source reuse would be a separate decision.

07 / Implementation sequence

Start with a complete, narrow loop.

The first useful app should let you speak or type to one slime, run a real Codex task, respond to it and return to the task later. Add providers and integrations after that loop is reliable.

Milestone 1 · Native core

One slime, one agent

  • Notch panel + menu-bar fallback
  • Color/name customization
  • Text chat and push-to-talk
  • Codex managed adapter
  • Approvals, questions and cancel
  • Local task/run history
  • Available Codex account limits

Exit test: a fixture-backed protocol suite and an explicitly authorized live session demonstrate input → execution → human response → persisted output.

Milestone 2 · Daily workspace

Projects and file snacks

  • Project roots + task board
  • PDF/text/image intake
  • Cited summaries and artifacts
  • File move/rename preview
  • Journal and recoverable operations
  • Queue and concurrency controls

Exit test: a sample folder produces an auditable summary and a reversible organization plan, including collision and interrupted-operation cases.

Milestone 3 · More agents

Claude, Pi and observers

  • Claude integration with supported auth
  • Pi RPC + extension UI bridge
  • Explicit capability negotiation
  • Opt-in external-session telemetry
  • Per-provider usage presentation
  • Provider switch via handoff brief

Exit test: two concurrent sessions cannot receive each other’s approvals, answers or completion events. Missing telemetry renders as unknown.

Milestone 4 · Connected work

Lark, Slack and Linear

  • Account connection + scope controls
  • Message/issue capture into tasks
  • Source-linked project context
  • Authorized outbound updates
  • Retry, deduplication and conflicts
  • Expanded media support

Exit test: a message becomes a task and its authorized result returns to the correct thread once, including reconnect and retry scenarios.

Defer until needed: team accounts and cloud synchronization, always-listening audio, a skin marketplace, agent-to-agent orchestration, autonomous folder watchers and a daemon that survives application quit. Each can be added without changing the core task/run/provider separation.

08 / Engineering contracts

Make the boundaries explicit.

Adapter protocol

Operations: discover capabilities, start, resume where supported, send input, answer a request, cancel and subscribe to events.

Events: run started, text delta, tool activity, approval requested, question requested, usage reported, artifact produced, run completed, provider error and connection lost.

Every event carries a provider ID, run ID, timestamp and applicable session/turn/request identifiers. Persist before updating UI; deduplicate replayed events.

Process and recovery rules

Use executable paths and argument arrays, not interpolated shell commands. Frame stdout protocol separately from stderr logs. Bound buffers and redact credentials.

Record process/session ownership. On relaunch, reconcile live processes and resumable sessions; mark unknown outcomes as interrupted. An app restart must not silently duplicate a task.

Approvals and questions

Show agent, project, tool and exact requested action. Handle multiple pending requests, free text and multiple-choice answers. Consume each answer once.

Expire requests when the provider resolves them, the turn ends or the channel closes. If delivery fails, show “not delivered”; do not pretend the action was approved.

Local data and permissions

Store project metadata, messages, run events, source references and operation journals locally. Keep account secrets out of model prompts and diagnostics.

Ask for microphone access when voice is first used. Use explicit folder selection for file work. Show when file content will be supplied to a cloud-backed CLI.

Notch behavior

Compact idle state; expanded state for chat; attention state for a pending request. Respect multiple displays, full-screen apps, display changes and Macs with no physical notch.

Provide a menu-bar fallback, keyboard access, reduced motion and text equivalents for every expressive state. Do not steal keyboard focus just because an agent emits a log line.

Verification priorities

Use recorded protocol fixtures for split JSON frames, stderr noise, failures, duplicate events, out-of-order completions and expired requests. Use temporary directories for move/collision/recovery tests.

Verify sleep/wake, network loss, account limits becoming stale and disappearing CLIs. Live tests using installed agents are separate opt-in checks that may consume account usage.
